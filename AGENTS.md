# Madeira Live Cams — інструкція проєкту

## 1. Мета продукту

**Madeira Live Cams** — вебзастосунок для мандрівників і локальних гідів на Мадейрі.

Продукт має одночасно:

- давати туристам актуальну картину острова через live-камери, погоду, маршрути, локації та практичні поради;
- бути щоденним робочим інструментом гіда: планування турів, перевірка умов, робота з групами, нотатки та корисні посилання;
- отримувати органічний трафік із Google та бути зрозумілим для AI-пошуку й LLM;
- бути швидким, мобільним, доступним та надійним.

## 2. Незмінні правила роботи з кодом

1. **Код замінюється тільки повністю.** Якщо погоджено зміну файлу, замінюйте весь його вміст цілісним готовим блоком. Не робіть точкових замін, пошуку/заміни фрагментів або ручного «дописування між рядками».
2. **Спочатку резервна копія, потім зміна.** Ніколи не редагуйте єдину копію файлу.
3. **Одна логічна зміна — один Git-коміт.** Приклад: `feat: add live camera directory`.
4. **Не ламати поточний проєкт.** Перед зміною перевіряйте збірку, типи, lint і ключові сторінки; після зміни — повторюйте перевірку.
5. **Не зберігати секрети в коді.** API-ключі, паролі й токени зберігаються тільки в `.env.local`; у Git додається лише `.env.example` без реальних значень.
6. **Не видаляти файли або залежності без явного рішення.** Спершу підтвердити причину, вплив і безпечний шлях видалення.

## 3. Безпечна повна заміна файлу у VS Code

### Перед початком

1. Відкрийте папку проєкту в VS Code: **File → Open Folder**.
2. Відкрийте вбудований термінал: **Terminal → New Terminal**.
3. Перевірте поточний стан Git:

```powershell
git status
git branch --show-current
```

4. Якщо є незакомічені зміни, зафіксуйте їх або тимчасово відкладіть. Не змішуйте стару незавершену роботу з новою задачею.
5. Створіть окрему гілку для задачі:

```powershell
git switch -c feature/short-description
```

### Створення резервної копії

Перед заміною кожного файлу створіть копію поруч із ним:

```powershell
Copy-Item "src/app/page.tsx" "src/app/page.tsx.bak"
```

Для важливого етапу також створіть Git-коміт до початку роботи:

```powershell
git add -A
git commit -m "chore: backup before homepage update"
```

Файли `*.bak` не мають потрапляти в основний код. Додайте до `.gitignore`:

```gitignore
*.bak
```

### Як замінити файл повністю

1. У провіднику VS Code відкрийте потрібний файл.
2. Натисніть `Ctrl+A` (виділити весь вміст).
3. Вставте **повний** новий код файлу.
4. Збережіть через `Ctrl+S`.
5. Відкрийте вкладку **Source Control** (`Ctrl+Shift+G`) і перегляньте diff. Він має відповідати задачі; не повинно бути випадкових змін у сторонніх файлах.
6. Запустіть перевірки проєкту (приклад для Next.js):

```powershell
npm run lint
npm run typecheck
npm run build
```

Якщо скриптів `typecheck` або `lint` немає, не вигадуйте їх: перегляньте `package.json` і запускайте тільки доступні команди.

7. Запустіть локальний сайт та перевірте змінену сторінку у браузері:

```powershell
npm run dev
```

8. Лише після успішної перевірки зробіть коміт:

```powershell
git add src/app/page.tsx
git commit -m "feat: rebuild Madeira landing page"
```

### Як відкотити невдалу зміну

Якщо новий файл не працює, відновіть резервну копію:

```powershell
Copy-Item "src/app/page.tsx.bak" "src/app/page.tsx" -Force
```

Якщо зміна вже закомічена, не використовуйте руйнівні команди. Створіть безпечний зворотний коміт:

```powershell
git revert <commit-hash>
```

## 4. Мінімальна структура продукту

### Публічна частина для мандрівників

- Головна сторінка: коротка цінність, популярні камери, поточні умови, маршрути й заклик спланувати день.
- Каталог live-камер: фільтри за регіоном, типом локації, станом погоди та доступністю.
- Сторінка кожної камери: відео/стрім, точна локація, час оновлення, погодні дані, опис, пов’язані маршрути й альтернативні камери.
- Напрямки: Фуншал, Піку-ду-Аріейру, Сейшал, Порту-Моніш, Санту-Антоніу-да-Серра, аеропорт та інші ключові райони.
- Гіди маршрутів: левáди, хайки, оглядові майданчики, пляжі, водоспади, безпечні маршрути на дощовий/вітряний день.
- Практичні сторінки: погода, безпека, транспорт, оренда авто, що взяти з собою, сезонність.

### Робоча зона гіда (після входу)

- Панель сьогоднішніх турів і погодних ризиків.
- Планувальник маршруту та чеклісти спорядження.
- Картка групи: учасники, контакти, обмеження, нотатки, статус оплати.
- Бібліотека перевірених локацій, парковок, туалетів, точок збору й запасних маршрутів.
- Шаблони повідомлень клієнтам: підтвердження, зміна плану через погоду, список речей.
- Журнал туру: фактичний маршрут, інциденти, фото/нотатки та підсумок.

Дані гідів, груп, телефонів, оплат і внутрішніх нотаток є приватними. Вони не індексуються та доступні лише авторизованим користувачам з потрібною роллю.

## 5. SEO та видимість у LLM

### Технічна основа

- Використовуйте серверний рендеринг або статичну генерацію для публічних сторінок. Основний текст не повинен з’являтися лише після JavaScript-завантаження.
- Кожна індексована сторінка має унікальні `title`, `meta description`, canonical URL, Open Graph та Twitter-метадані.
- Створіть `sitemap.xml` і `robots.txt`. У sitemap додаються тільки канонічні публічні URL.
- Закриті розділи (`/guide`, `/admin`, сторінки клієнтів, чернетки) захищаються авторизацією і виключаються з індексації через `noindex`.
- Додайте структуровані дані Schema.org відповідно до типу сторінки: `TouristAttraction`, `Place`, `VideoObject`, `FAQPage`, `BreadcrumbList`, `Article`.
- Оптимізуйте Core Web Vitals: стиснуті зображення, ліниве завантаження важких медіа, мінімум сторонніх скриптів, стабільний layout.
- Забезпечте повну мобільну адаптивність і доступність: семантичні заголовки, alt-тексти, контраст, керування з клавіатури.

### Контент, який приваблює органічний та AI-трафік

- Створюйте корисні сторінки під реальні запити: “weather in Madeira today”, “best Madeira webcams”, “is Pico do Arieiro open”, “Madeira levada walk conditions”.
- На кожній ключовій сторінці прямо відповідайте на запит у перших абзацах, потім давайте перевірені деталі, дату оновлення, автора/джерело та пов’язані посилання.
- Пишіть конкретно: назви місць, висота, складність, тривалість, сезон, обмеження, план B. Не створюйте масові шаблонні сторінки без унікальної користі.
- Додавайте блоки FAQ з короткими точними відповідями, але не дублюйте один і той самий текст на багатьох URL.
- Вказуйте дату та час останньої перевірки для камер, погоди, стану маршрутів і тимчасових обмежень.
- Посилайтеся на першоджерела для безпеки та офіційних обмежень. Не вигадуйте статуси маршрутів, розклад або погодні дані.
- Мова сайту: стартово англійська для міжнародного трафіку; архітектура має підтримувати PT, DE, FR, ES та UK. Для перекладів потрібні окремі URL і `hreflang`.

### Заборонено

- приховувати текст, купувати посилання, генерувати сторінки під ключові слова без редакторської цінності;
- копіювати чужі описи, фото або відео без дозволу й атрибуції;
- індексувати персональні дані чи сторінки, що потребують входу;
- обіцяти безпеку маршруту без дати перевірки та джерела.

## 6. Дані та надійність

- Для кожної камери зберігайте: назву, координати, регіон, URL джерела, ліцензію/дозвіл, статус, час останнього успішного оновлення, резервне зображення.
- Якщо стрім недоступний, показуйте чесний стан “temporarily unavailable”, час останньої перевірки та альтернативні камери — не порожній блок.
- Дані про погоду й перекриття маршрутів мають мати джерело, час отримання і зрозумілий fallback у разі збою API.
- Перед інтеграцією сторонніх камер перевіряйте умови використання, вбудовування та авторські права.

## 7. Критерії готовності кожної зміни

Зміна вважається готовою, лише якщо:

- є резервна копія або попередній Git-коміт;
- весь цільовий файл замінено як єдиний завершений варіант;
- `git diff` переглянуто;
- збірка, lint і перевірка типів проходять (якщо налаштовані);
- сторінка перевірена на desktop і mobile;
- у публічної сторінки є коректні SEO-метадані, семантична структура й зрозумілий URL;
- немає витоку секретів або персональних даних;
- зміна зафіксована окремим Git-комітом.

## 8. Робочий принцип для AI-асистента або розробника

Перед реалізацією кожної задачі коротко фіксуйте:

1. Що буде змінено і які файли зачеплено.
2. Які файли замінюються повністю.
3. Який backup/коміт існує до початку.
4. Як зміна впливає на SEO, швидкість, приватність і мобільний UX.
5. Які команди та сценарії перевірки виконано після зміни.

Якщо вимога суперечить цим правилам, пріоритет: безпека даних → працездатність застосунку → SEO-якість → швидкість реалізації.
